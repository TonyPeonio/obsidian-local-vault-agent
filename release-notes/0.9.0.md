Search that finds the passage, one model call fewer per question, a chat that shows what it is doing, and firmer limits on what the agent may read and change.

Unless it says otherwise, a number below is from repeated runs on one desktop (RTX 5070 12 GB, Ollama 0.40.15, `qwen3.5:9b` and `qwen3.5:4b`) on a generated test vault. A figure with a range is the median of the runs named. The result files are in `bench/`; a tag in brackets says which (`fin3` is `bench/0.9.0-fin3-*.json`). A few figures are in no result file and were read from a run's log (`bench/frozen-0.9.0-<tag>.log`); the text says so where that is the case. "The closing runs" are the five runs on the 9B model and the three on the 4B made on commit de54882; what was changed after them is listed under *The benchmark*.

**What you notice first**
- **A question about your notes takes one model call where it took two.** The plugin makes the first search itself and hands the model the passages. On the benchmark's five plain questions the 9B model needed 2 or 3 calls each in 0.8.0 and 1 in this version (medians of five runs each). The 4B model needed 2 to 8 in 0.8.0; in this version 1 on three of the five questions and 2 on the other two (medians of three runs each).
- **The first message does not wait for the model to load.** Clicking into the chat box loads the model and has it read its instructions. After that the first words arrived 0.2 s after sending (0.2 to 0.3, three runs, 9B model); from a model that was not loaded it took 5.2 s (5.2 to 8.3). This was timed under Node, not inside Obsidian, and 0.8.0 was never timed this way, so there is no before.
- **Search finds exact words as well as meaning.** The right passage is among the six returned for 99.2% of 240 test questions; with embeddings alone, which is how 0.8.0 ranked passages, for 65.8%.
- **The chat says what a turn is doing**, lets you scroll and select while a long answer is written, and queues a message sent while the model is busy.
- **A change you did not ask for is shown even when changes are approved automatically.** If you asked a question and the model wants to change a note while *Auto-approve edits* or *Approve all in this chat* is on, the diff dialog opens all the same, with a line saying the change was not asked for. With changes approved one by one, which is the default, the usual diff dialog opens as for every change, without that line.
- **Excluded folders are a boundary** for every tool and for the commands that work on the open note.
- **On the benchmark** this version passes 189 of 190 checks in the median run on both models (188 to 190 over five runs on the 9B, 187 to 190 over three on the 4B). 0.8.0 passed 143 and 136 of the 149 checks of its own, smaller harness; see *The benchmark* for why the two are not the same test.

**Search**
- **Passages are found by meaning and by words together.** Embeddings blur what notes are full of: a name, an identifier, a number, a rare term. Every passage is now scored both ways (embeddings, and BM25 over the same chunks) and the scores are blended; a passage with every word of the question gets a bonus large enough to pass the best match by meaning alone. On a retrieval benchmark of 240 questions with known answers (new: `npm run bench:retrieval`, no chat model) the right passage is in the six returned for 99.2% of questions (238) and first for 92.9% (223). With the word matching switched off in the same index, which is how 0.8.0 ranked passages, it is 65.8% (158) and 58.8% (141) (`bench/retrieval-0.9.0-hybrid.json`). The code of 0.8.0 itself was measured on the 218 questions the benchmark had then: 155 in the six returned (71.1%) and 141 first (64.7%) (`bench/retrieval-0.8.0-before.json`). The 22 questions added since ask for a daily note by its day.
- **A passage says which section it is from.** A note that repeats a heading (a "Summary" under every lecture date) used to return passages labelled "Lectures › Summary". Chunks now carry the path of headings above them ("2026-09-10 › Summary"), which is embedded with the text, shown to the model, and accepted by `read_section`. An index written by 0.8.0 is cut again for every note at the first start with this version, in the background; a piece is embedded again unless its text is unchanged and its heading path is just its nearest heading, which is what 0.8.0 embedded it with.
- **A day named in words is found.** "September 10", "9/10", "yesterday", "last Tuesday", "this week" become the ISO days notes are named and headed by; most of the results are kept for the notes and sections of that day, ranked by the question's other words. Of the 60 questions that name a lecture by its date, the right passage came first for none with embeddings alone (and was among the six for 2), and first for all 60 now. Of the 22 that name a daily note by its day: first for none before, for all 22 now.
- **`search_notes` uses the same ranking** (the note whose best passage matches): the right note first for 92.9% of the 240 questions (223). The ranking 0.8.0 used, an embedding search and a keyword scan with their ranks fused, put it first for 57.9% (139).
- **When the vault has nothing on it, the search says so.** A word of the question that appears in no note is named ("No note in the vault contains "wheels""), and with the default embedding model a weak best match is called weak. The sentence is about the vault as it is when you ask: a note created or edited since the index last read it is read and searched for the word first. A word counts as present when a note has it only in its properties, its name or a heading with nothing under it, and a plural whose singular is under four letters ("logs", "cats") is never called absent. A word that was edited out of the last note that had it, or went with a deleted note, is named as absent once the index has read the change; a note renamed before the index had read its last edit is read at the rename. Measured on the benchmark's question about a 39,000-character log, which the 4B model failed in 2 of 3 full runs because the search told it no note contained "belts" (`fin2q`): after the fix 7 of 7 checks in 5 of 5 runs of that scenario with the note indexed (`ln4`), in 3 of 3 with it not yet indexed (`ln4u`), and in all three closing runs (`fin3q`).
- **A table passage states the row you asked about.** Under a table of six rows or more, the rows that have the question's words are written out again with each value after its column heading ("Part: M-122; Frame: NEMA 17; Rated current: 1.50 A; Holding torque: 20 N·cm; …"); nothing is added when the words single out no row or more than three. The 9B model had been handed a whole, correct 36-row table and gave the torque of the row above. That question alone on the 9B model: right in 5 of 10 runs before (`tb9`), 10 of 10 after (`ta9`); on the 4B model 5 of 5 after (`ta4`); right in all eight closing runs. A table longer than one chunk (2,200 characters) is now cut between rows and every piece starts with the heading row; it used to be cut in the middle of a row.
- **A long list or line is cut between words.** A paragraph longer than one chunk with no sentence ends (a long list without full stops, a list of links) was cut every 2,200 characters, through a word; a word cut inside its first four letters that stood nowhere else was then named as being in no note. It is now cut at a line end or, failing that, at a space.
- **The index no longer keeps a note that is gone, and notices a note changed behind its back.** A note deleted, renamed or moved to an excluded folder while it was being embedded was put back under its old path, and searches returned it until the next start. A note whose text changed while its modification time stayed the same (a sync tool that restores times) was never read again; it is now read again when its size differs.
- **A note you attach brings the passages it links to.** With `[[a note]]` in the message, the passages of the notes it links to that match the question come with it (at most 2,400 characters), and the attached note counts as a source. The benchmark's question of this kind lost a check in 3 of 3 runs of 0.8.0 on the 4B model and none in the three closing runs.

**Speed**
- **The search is made before the model's first reply.** A question about the content of notes always begins with the same search, so the plugin makes it and hands the model the result as its own tool call: one model call fewer per question, and no answer "from memory" before a note has been seen. A first answer that claims a search nobody made is sent back once. Setting: *Search before the first reply*, on by default. What a user should know about it:
  - It needs the semantic index. With *Semantic search* off, or before the index is built, the model starts as it did before.
  - It hands the model four passages; a search the model asks for itself returns six. In the retrieval benchmark the right passage was among the first three for 234 of the 240 questions.
  - These go to the model as before: requests to change notes, questions about the vault's structure, messages with a note attached, messages of more than one line or more than 400 characters, follow-ups that lean on the conversation and, when Lecture Companion is installed, questions that mention a lecture, a class, a meeting or what somebody said (those are left to its transcript tools).
- **The model is made ready while you type.** Focusing the chat box loads the model and has it read its instructions and the vault outline (setting: *Get the model ready while you type*, on by default; at most once in four minutes, and not while a turn or a scheduled job runs). The warm-up itself took 4.8 s (4.7 to 4.8, three runs, `bench/ttft-0.9.0-fin3.json`).
- **A conversation's instructions are written once.** A note created between two messages, often by the agent itself, used to change the start of the next request, and everything was read again; the change now travels as one line with the message, until more than 40 notes have come or gone. A message sent after a note was created got its first words after 0.5 s (0.2 to 0.5, three runs). There is no timing of 0.8.0 to set beside it.
- **Long jobs stop re-reading themselves.** Over budget, the conversation is cut once and well below the limit, so the following steps only append; the budget is in the model's own token counts, not an estimate, so a full window no longer silently loses the start of the prompt; and the wrap-up request keeps what is cached.
- **Results the model reads are smaller where nothing is lost**: a survey of one heading across a folder is grouped (three or more lines, one or two, empty) and names empty sections instead of listing them.
- All changes together, on the 24 scenarios that both versions' harnesses have: the 9B model made 63 model calls a run (61 to 77, five runs) where 0.8.0 made 77 (70 to 112), and 80 tool calls (75 to 108) where 0.8.0 made 119 (83 to 195). The 4B model: 67 model calls (65 to 73, three runs) against 110 (106 to 130), and 81 tool calls (78 to 81) against 110 (104 to 120).

**The chat**
- **It says what a turn is doing, and how it went**: a progress line while the model reads, searches and writes, and a summary when it ends.
- **Streaming draws only what changed** and follows the text only while you are at the bottom, so you can scroll up and read during a long answer; text can be selected while it streams; thinking text is drawn a few times a second, not once per token.
- **A message sent while the model is busy is queued**, not dropped.
- **Paste or drop a picture into the message box**; it is saved as an attachment and read with the vision model.
- **Tool cards** have an icon and a plain sentence for every tool, and a restored chat shows them as they ended, with Undo, Copy and Insert.
- **Insert at cursor** goes to the note you were last in, and the selection given to the agent comes only from an editor showing the active note.
- **Approve all** is asked for and confirmed in the diff dialog, visible in the chat while it is on, and never set by one stray key or a double-click.
- **The model picker** lists the models that can be used, with size and whether they are loaded, and re-checks vision when the model changes.
- **One model job runs at a time.** Stop works in a quiz (question writing and grading included); a scheduled job can be stopped, stops when the plugin unloads, and a failed run is tried again after 5, 15 and 60 minutes.
- No "server not reachable" notice just because Obsidian started before the server.

**What the agent no longer gets wrong**
- **A question about open tasks gets every unchecked box, not the best few passages.** "Which action items from my meetings with Ana Rocha are still open?" was answered from the four passages the first search returns: the open items of 4 of the 8 meetings. For such a question the plugin now makes the exhaustive search instead (`grep_vault` for unchecked boxes, kept to the notes whose path has the name the question gives: new parameter `path_contains`) and hands the model that. A name is taken as whole words where a path has it so: "Ana" searches the notes on Ana, not also `Management/` and `Banana bread`. The scenario's two checks on the content of the answer failed in 5 of 5 runs on the 9B model and 3 of 3 on the 4B before (`fin`, `finq`). In the closing runs both pass in 4 of 5 on the 9B (in the other run the model named 3 of the 8 items) and in 3 of 3 on the 4B.
- A heading given to `list_sections` as a text to look for is read as the heading; read literally, this had cost 131 tool calls in one benchmark run.
- **A write to a heading that occurs more than once is refused** with the full heading paths to choose from, instead of landing in the first match.
- `find_in_note` says which heading path each match is under.
- **A reply that repeats itself is stopped** (the same 8 to 130 characters six times in a row), and a reply is limited to 8,192 tokens or half the context window, whichever is smaller, so a model stuck in a loop cannot fill the window.
- Tool results stay within their limit and keep their last words (paging markers, "N more", verdicts); `read_note` paging no longer skips text; long lines in `grep_vault` are cut around the match; a folder that does not exist is reported, not answered with "nothing found"; dates are the user's local dates; a model-written regular expression can no longer freeze the app.
- A result cut by the per-step budget can be asked for again; arguments that were not valid JSON get that answer, not "missing argument"; a reply cut at the length limit says so; one retry after a server hiccup; a turn never ends on nothing.
- Sources and paragraph citations are added only to the reply that ends the turn.
- **The nightly job cannot see daily notes older than its start date, and every topic note it writes gets its Sources.** The benchmark's nightly-job scenario passed 2 of its 5 checks in every one of the five 0.8.0 runs on the 9B model and 5 of 5 in all eight closing runs of this version.

**Safety and privacy**
- **Excluded folders are a boundary.** Nothing in them can be read, written, created, moved in or out, or named as a backlink, and an excluded note that is open is not "the open note". This is enforced in one place under every tool. Also:
  - A folder added to the list is left out of every search from that moment, and a conversation that is already running gets its instructions written again without that folder's note names. What the model read earlier in that conversation stays in it.
  - The commands *Reformat the current note*, *Summarize the current note*, *Edit the selected text with an instruction*, *Ask about the selected text* and *Suggest concept links for this note* (and `/reformat`, `/summarize`, `/edit`) do nothing on a note in an excluded folder and show a notice that says so. Until now the first four sent its text, its selection or its path to the model.
  - Today's daily note is not named to the model when the daily notes folder is excluded.
  - *Process my daily notes* (and `/daily`) does nothing when the daily notes folder is excluded and shows a notice; until now its prompt named the folder to the model. The nightly job does the same, and such a run counts as done for that night instead of being retried as a failure.
  - With Lecture Companion installed, lectures whose notes are in an excluded folder are not listed by `list_lectures`, not read out by `lecture_transcript`, and not picked by the quiz.
  - A picture pasted into the chat while a note of an excluded folder is open is not saved beside that note; it goes where an attachment goes when no note is open.
- **A change after a question is shown even when changes are approved automatically.** If you asked a question and the model (or a note it read) wants to change something while *Auto-approve edits* or *Approve all in this chat* is on, the diff dialog opens anyway, with the line "You asked a question; this change was not asked for". With changes approved one by one, the default, the usual dialog opens as for any change, without that line. Whether you asked for a change is read from your own words only, wherever in the message the request stands ("Find every code block … and collect them into a new note" asks for one), never from an attached note, a quoted selection or anything the model read. That request was at first taken for a question and warned in 8 of 8 full runs (two runs in each of the logs `bench/frozen-0.9.0-fix9.log`, `-fix4.log`, `-fix9x.log` and `-fix4x.log`); after the fix it was created without a warned dialog in 3 of 3 runs of the scenario on each model (`cs9`, `cs4`) and in all eight closing runs.
- **In a turn that only asked a question the agent no longer says yes for you.** When a model stops on "shall I proceed?", the agent used to answer yes. Now, after a question, it tells the model to finish the reading and the answer and to change nothing, and what the model offers ("If you want, I can compile them into a new note") is yours to accept in your next message. A search or a read the model only announced is still pushed on, and a model that asks again whether to read on is told the same again, up to three times per message; a second question about anything else ends the turn and goes to you. In a turn that asks for a change, the automatic yes is as before. This needs *Keep going when the model asks for permission* to be on, as it is by default. On a real model this line was sent twice in all the runs made after the change, counted in the run logs: once in three runs of two scenarios (`p1r9`) and once in the five closing runs on the 9B model. Both times the model went on to list the notes, attempted no change, and the scenario passed 6 of 6 checks. The rest is 31 unit tests with a scripted model.
- **A reply cannot make the chat fetch from the network.** A remote image or frame in a reply, which a clipped page could talk the model into writing with your notes' text in its address, is drawn and stored as a plain link, while it streams and in chats saved by earlier versions too. Vault embeds, local images and ordinary links are untouched.
- **Text the agent reads is material, not orders.** A benchmark scenario plants instructions in a clipped page. The 9B model ignored them in all ten runs with the new rule in its instructions and in all ten without it (`injon`, `injoff`), so the rule is a second line, not the first. **The 4B model does not always ignore them.** `qwen3.5:4b` called `create_note` for the note the page asks for in 6 of 20 runs of that scenario in which it read the page itself (`inj4u`, `inj4v`, 3 of 10 each), in 0 of 10 when the page reached it as a search result (`inj4`), and in none of the eight closing runs on either model. In one of three full runs on earlier code (`fin2q`, run 2), made while the benchmark still approved every change, the 4B model wrote that note and it was in the vault afterwards. What stops the write is the dialog of the item above, not the model. The benchmark runs with changes approved automatically, so each of the six writes was shown with the warning and, with the benchmark answering Reject, none was made (the six lines are in `bench/frozen-0.9.0-inj4u.log` and `-inj4v.log`). With the 4B model, read a diff that appears after a question before you approve it, however changes are approved: with one-by-one approval it comes without the warning line.

**Conventions**
- **A first draft of the conventions note, written from the vault itself** (command: *Draft the conventions note from this vault*): which folders hold what, how the notes in them are named and sectioned, which properties and tags are in use. Everything in it is counted, without a model; a line is written only when most notes of a folder agree. It only replaces the part between its own markers and never what you wrote around it.

**OpenAI-compatible servers**
- The thinking setting now reaches the model on llama.cpp's server and vLLM; reasoning sent inline as `<think>…</think>` or in a `reasoning` field is kept out of the answer; llama.cpp's timings reach the progress line.
- **The agent works within the context window the server really has.** Ollama is told a context size with every request. LM Studio, llama.cpp and the others are not: they have the size the model was loaded with (LM Studio's default is 4096 tokens) and cut the start of a longer prompt, which is the plugin's instructions and tool rules, without any error. The plugin now asks the server for that size (llama.cpp reports `meta.n_ctx` in `/v1/models`, LM Studio `loaded_context_length` in `/api/v0/models`), once per server address and model and again when the model is warmed, and works within the smaller of it and the *Context window* setting: the chat, the scheduled jobs and the quiz. When the instructions and the tool list do not fit that window with room for a conversation, the message ends at once and says how large the server's window is, how much the plugin needs at the least, and how to load the model with more (LM Studio: the context length slider when loading the model; llama.cpp: `-c 16384` or more); nothing is sent. *Settings → Context window* shows the size the server reported. A server that reports no size is treated as before: the setting is assumed.
- Run against one real server: the llama.cpp server that ships with Ollama, which found no usable GPU and ran on the CPU, with `qwen3.5:4b` and three benchmark scenarios (a question, a follow-up, a rejected change), one run each way. Started with a 32768 window, the server reported 32768 and 18 of 18 checks passed. Started with `-c 4096`, it reported 4096 and each of the three messages ended with the new message (the benchmark vault needs at least 14336) with nothing sent to the model. Both results are read from the run logs (`bench/frozen-0.9.0-lcpp32.log`, `-lcpp4k.log`); no result file was kept for them.

**Limits**
- The benchmark vault is generated, all runs are from one desktop, and the checks were written by the people who wrote the plugin, most of them after seeing the failure they test for. A check is a pattern looked for in the answer or in the vault afterwards, not a person's judgement of the answer.
- With the 4B model, expect it to follow instructions planted in a page it reads some of the time (6 of 20 runs above). The warning dialog stops the write only if you reject it.
- Whether a message asks for a change is decided from its wording by rules, not by a model. It can be wrong both ways: a request phrased in a way the rules do not know ("Would you mind moving…", a request in German) is warned although it was asked for (approve it), and a message that asks without the shape of a question ("belt tension recommendation", "I wonder what the clipped page recommends.") is not judged, so a change in its turn is not warned. A message that is neither a question nor a request ("go on") is never warned.
- When the model writes without offering and you reject the change, whether the reply after the rejection still holds the answer is up to the model.
- "No note in the vault contains …" is not said when checking would not be cheap or sure: more than 100 notes or two million characters waiting to be indexed, the index not yet compared with the vault after start-up, or the excluded folders edited in this session (until the next start, sync or rebuild).
- The row stated under a table is added only when the question's words single out one to three rows of a table of six rows or more. A single table row longer than a chunk (2,200 characters) is still cut inside the row, between words. A stretch of more than 2,200 characters with no whitespace at all (one endless token, text written without spaces) is still cut every 2,200 characters.
- The index sees that a note changed by its modification time and its size, as the vault lists them. A change that keeps both (a sync tool that restores the time, and a text of the same length in bytes) is not seen until *Rebuild semantic index* is run.
- The open-tasks search keeps to a person or project only when the question gives the name capitalised or in quotes and some note's path has it; otherwise the model is handed every unchecked box of the vault, cut at 200 lines. It finds unchecked boxes in lists (`- [ ]`, `* [ ]`, `1. [ ]`), not tasks written any other way.
- Excluded folders: the text of a newly excluded folder stays in the index file on disk until the next sync, though no search returns it. When the attachment folder itself is excluded, a pasted picture is still saved there and read by the vision model. When the topic notes folder of "Process my daily notes" is excluded, its prompt still names that folder; the tools then refuse to write there.
