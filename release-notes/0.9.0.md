Search that finds the passage, one model call fewer per question, a chat that shows what it is doing, and a long list of things the agent can no longer get wrong.

**Search**
- **Passages are found by meaning and by words together.** Embeddings blur exactly what notes are full of: a name, an identifier, a number, a rare term. Every passage is now scored both ways (embeddings, and BM25 over the same chunks) and the scores are blended; a passage with every word of the question gets a bonus large enough to pass the best match by meaning alone. On a retrieval benchmark of 240 questions with known answers (new: `npm run bench:retrieval`, no chat model, seconds per run) the right passage is in the six returned for 99.2% of questions, up from 65.8%, and first for 92.9%, up from 58.8%.
- **A passage says which section it is from.** A note that repeats a heading (a "Summary" under every lecture date) used to return passages labelled "Lectures › Summary". Chunks now carry the path of headings above them ("2026-09-10 › Summary"), which is embedded with the text, shown to the model, and accepted by `read_section`. An index from an earlier version is brought up to date in the background: only sections whose path changed are embedded again.
- **A day named in words is found.** "September 10", "9/10", "yesterday", "last Tuesday", "this week" become the ISO days notes are named and headed by; most of the results are kept for the notes and sections of that day, ranked by the question's other words. Questions that name a lecture by its date went from 0 of 60 to 60 of 60.
- **`search_notes` uses the same ranking** (the note whose best passage matches): the right note first for 92.9% of questions, 57.9% before.
- **When the vault has nothing on it, the search says so.** A word of the question that appears in no note at all is named ("No note in the vault contains "wheels""), and with the default embedding model a weak best match is called weak.
- **A note you attach brings the passages it links to.** With `[[a note]]` in the message, the passages of the notes it links to that match the question come with it, and the attached note counts as a source.

**Speed**
- **The search is made before the model's first reply.** A question about the content of notes always begins with the same search, so the plugin makes it and hands the model the result as its own tool call: one model call fewer per question, and no answer "from memory" before a note has been seen. Requests to change notes, questions about the vault's structure, messages with a note attached and follow-ups that lean on the conversation go to the model as before. Setting: *Search before the first reply*.
- **The model is made ready while you type.** Focusing the chat box loads the model and has it read its instructions and the vault outline (setting: *Get the model ready while you type*).
- **A conversation's instructions are written once.** A note created between two messages, often by the agent itself, used to change the start of the next request, and everything was read again; the change now travels as one line with the message.
- **Long jobs stop re-reading themselves.** Over budget, the conversation is cut once and well below the limit, so the following steps only append; the budget is in the model's own token counts, not an estimate, so a full window no longer silently loses the start of the prompt; and the wrap-up request keeps what is cached.
- **Results the model reads are smaller where nothing is lost**: a survey of one heading across a folder is grouped (three or more lines, one or two, empty) and names empty sections instead of listing them.

**The chat**
- **It says what a turn is doing, and how it went**: a progress line while the model reads, searches and writes, and a summary when it ends.
- **Streaming draws only what changed** and follows the text only while you are at the bottom, so you can scroll up and read during a long answer; text can be selected while it streams; thinking text is drawn a few times a second, not once per token.
- **A message sent while the model is busy is queued**, not dropped.
- **Paste or drop a picture into the message box**; it is saved as an attachment and read with the vision model.
- **Tool cards** have an icon and a plain sentence for every tool, and a restored chat shows them as they ended, with Undo, Copy and Insert.
- **Insert at cursor** goes to the note you were last in, and the selection given to the agent comes only from an editor showing the active note.
- **Approve all** is asked for and confirmed in the diff dialog, visible in the chat while it is on, and never set by one stray key or a double-click.
- **The model picker** lists the models that can be used, with size and whether they are loaded, and re-checks vision when the model changes.
- **One model job runs at a time.** Stop works in a quiz (question writing and grading included); a scheduled job can be stopped, stops when the plugin unloads, and a failed run is tried again after 5, 15 and 60 minutes.
- No "server not reachable" notice just because Obsidian started before the server.

**Things the agent can no longer get wrong**
- Answering the first question without searching ("I found this by searching…" with no tool call) is caught and sent back.
- **A question about open tasks gets every unchecked box, not the best few passages.** "Which action items from my meetings with Ana Rocha are still open?" was answered from the four passages the first search returns: the open items of 4 of the 8 meetings, in every benchmark run on both models. For such a question the plugin now makes the exhaustive search instead (`grep_vault` for unchecked boxes, kept to the notes whose path has the name the question gives: new parameter `path_contains`) and hands the model that.
- A heading given to `list_sections` as a text to look for is read as the heading; this had cost 131 tool calls in one run.
- **A write to a heading that occurs more than once is refused** with the full heading paths to choose from, instead of landing in the first match.
- `find_in_note` says which heading path each match is under.
- **A reply that repeats itself is stopped**, and replies have a length limit that follows the context size, so a model stuck in a loop cannot fill the window.
- Tool results stay within their limit and keep their last words (paging markers, "N more", verdicts); `read_note` paging no longer skips text; long lines in `grep_vault` are cut around the match; a folder that does not exist is reported, not answered with "nothing found"; dates are the user's local dates; a model-written regular expression can no longer freeze the app.
- A result cut by the per-step budget can be asked for again; arguments that were not valid JSON get that answer, not "missing argument"; a reply cut at the length limit says so; one retry after a server hiccup; a turn never ends on nothing.
- Sources and paragraph citations are added only to the reply that ends the turn.
- The nightly job cannot see daily notes older than its start date, and every topic note it writes gets its Sources.

**Safety and privacy**
- **Excluded folders are a boundary.** Nothing in them can be read, written, created, moved in or out, or named as a backlink, and an excluded note that is open is not "the open note". Enforced in one place under every tool.
- **A change after a question is always shown.** If you asked a question and the model (or a note it read) wants to change something, the diff dialog opens even when changes are approved automatically.
- **A reply cannot make the chat fetch from the network.** A remote image or frame in a reply, which a clipped page could talk the model into writing with your notes' text in its address, is drawn and stored as a plain link, while it streams and in chats saved by earlier versions too. Vault embeds, local images and ordinary links are untouched.
- **Text the agent reads is material, not orders.** A benchmark scenario plants instructions in a clipped page; the 9B model ignored them in all ten runs with the new rule and in all ten without it, so the rule is a second line, not the first.

**Conventions**
- **A first draft of the conventions note, written from the vault itself** (command: *Draft the conventions note from this vault*): which folders hold what, how the notes in them are named and sectioned, which properties and tags are in use. Everything in it is counted, without a model; a line is written only when most notes of a folder agree. It only replaces the part between its own markers and never what you wrote around it.

**OpenAI-compatible servers**
- The thinking setting now reaches the model on llama.cpp's server and vLLM; reasoning sent inline as `<think>…</think>` or in a `reasoning` field is kept out of the answer; llama.cpp's timings reach the progress line. The request format was checked by hand against the llama.cpp server that ships with Ollama.
- **The agent works within the context window the server really has.** Ollama is told a context size with every request. LM Studio, llama.cpp and the others are not: they have the size the model was loaded with (LM Studio's default is 4096 tokens) and cut the start of a longer prompt, which is the plugin's instructions and tool rules, without any error. The plugin now asks the server for that size (llama.cpp reports `meta.n_ctx` in `/v1/models`, LM Studio `loaded_context_length` in `/api/v0/models`), once per server address and model and again when the model is warmed, and works within the smaller of it and the *Context window* setting: the chat, the scheduled jobs and the quiz. When the instructions and the tool list do not fit that window with room for a conversation, the message ends at once and says how large the server's window is, how much the plugin needs at the least, and how to load the model with more (LM Studio: the context length slider when loading the model; llama.cpp: `-c 16384` or more); nothing is sent. *Settings → Context window* shows the size the server reported. A server that reports no size is treated as before: the setting is assumed.
- Tried against the llama.cpp server that ships with Ollama, with `qwen3.5:4b` and three benchmark scenarios (a question, a follow-up, a rejected change) through the OpenAI path. Started with a 32768 window, the server reported 32768 and 18 of 18 checks passed. Started with `-c 4096`, it reported 4096 and each of the three messages ended with the new message (the benchmark vault of 337 notes needs at least 14336) with nothing sent to the model.

**Benchmark**
- The first full runs of 0.8.0 on the RTX 5070: 143 of 149 checks (141 to 144 over five runs).
- This version, the same 149 checks plus 8 for the injection scenario: 154 of 157 (150 to 156 over four runs), with 12% fewer model calls and a quarter fewer tool calls. Those runs are from the middle of the work (commit f506322); see *Not verified* for what was not repeated.
- Four new scenarios on awkward notes (a 39,000-character log, a table, two notes with one name, properties): 27 of 27 checks in the median run.
- One run of the whole suite as it now stands (190 checks with the awkward-note and open-tasks scenarios) on the finished agent code, before the chat-panel work was merged in: 185 of 190. The five misses: the drawn "47" read as "41" (a fault of the test picture, in every run since 0.7.0), one tool call more than allowed on one question, the daily-note survey listing too many one-line days, the list of lectures with unsummarised recordings left out of one answer, and the lecture clean-up removing 16 of 18 recordings where 17 are required.
- The open-tasks question after the closing runs: its two checks on the content of the answer (at least 80% of the 8 distinct open items, the meetings they are from) failed in 5 of 5 runs on `qwen3.5:9b` and 3 of 3 on `qwen3.5:4b`. With the exhaustive search both pass in 4 of 5 runs on the 9B model (the other run listed only the items assigned to Ana Rocha, 3 of the 8) and in 3 of 3 on the 4B. Two full runs on the 9B model with it: 186 and 188 of 190, where the five closing runs had 184 to 187 (median 185); the other 29 scenarios scored 180 and 182 of 184, within the closing runs' 180 to 183.
- The picture of the read-image scenario is redrawn: the number is written in thick round strokes in print shapes, 560 by 420 pixels (`scripts/whiteboard-png.ts`), where it was a 5×7 bitmap scaled up whose 7 was a one-cell bar on a staircase. With the old picture `qwen3.5:9b` failed "reads the number 47" in 7 of 7 full runs; it reads the new one as 47 in 3 of 3 runs of the scenario, so the miss was the drawing's. Not measured on the 4B model.
- New: results record which checks failed and the answers; repeated runs are summarised with median and spread; the characters the model must read are counted independently of the machine's load; scenarios on open tasks and prompt injection; `bench:retrieval`, `bench:ttft`.
